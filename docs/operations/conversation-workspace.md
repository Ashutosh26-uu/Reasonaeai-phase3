## File and preview data flow

Files, saved diffs, and a running app use different data paths:

```mermaid
sequenceDiagram
    participant CTO as Main CTO
    participant W as Worker
    participant S as Run sandbox and /workspace volume
    participant CP as Private Git checkpoint store
    participant DB as PostgreSQL event/history ledger
    participant API as Authenticated product API
    participant UI as Conversation workspace
    participant GW as Preview API relay

    W->>S: Restore selected conversation checkpoint; mount run workspace
    CTO->>S: Normal file/shell tools mutate /workspace; optional starter is copied only for explicitly selected Next.js
    W->>S: At run end, snapshot Git tree and build checkpoint bundle
    W->>CP: Store immutable checkpoint bundle
    W->>DB: Publish checkpoint id/manifest on terminal run event
    UI->>API: GET workspace/tree (authenticated, project-scoped)
    API->>DB: Resolve conversation's selected saved checkpoint
    API->>CP: Read verified tree/blob objects
    API-->>UI: File list or selected file content
    UI->>API: GET checkpoint-diff with run id + saved event sequence
    API->>DB: Verify event provenance and tenant/project scope
    API->>CP: Compare saved file against checkpoint base
    API-->>UI: Bounded text diff

    CTO->>S: Start app and call open_preview with exact localhost URL
    CTO->>S: Probe selected app and write .reasonate/preview.json
    CTO->>DB: Register run-scoped preview lease before tool returns
    UI->>API: POST build-session preview (authenticated, scoped)
    API->>S: Reattach to the same run sandbox; verify selected app port
    API->>S: Start relay on reserved container port 18080
    API-->>UI: Preview id, status, selected app port, scoped API URL
    UI->>API: Poll authorized preview status; load scoped preview URL
    API->>S: Relay only to the selected app port
    UI->>API: Request authenticated, same-host WebSocket upgrade
    API->>S: Tunnel handshake and frames through the existing relay
```

Model file/shell tools and the app process all operate in the same mutable `/workspace` volume of the run sandbox. The Docker adapter declares the private relay port when that sandbox is created; opening a preview attaches to that container and starts the relay in it. It does not create a browser container or a second app sandbox. The panel address represents the sandbox app, for example `http://localhost:4173/`; the host-assigned relay port, preview gateway URL, and API port are transport details and must not be presented as the app URL. The address bar accepts this selected sandbox localhost URL or a project route such as `/settings`; navigation still travels through the scoped preview gateway. `browser_verify` accepts the selected run's sandbox app or relay URL and maps it to the same authorized gateway; it does not contact an arbitrary private address.

The Files and Changes views are checkpoint-backed. They do **not** stream uncheckpointed edits while a model is still writing. An accepted feature for live pre-checkpoint file trees/diffs needs a scoped, lease-fenced worker filesystem event/read path that covers tool writes, shell writes, and delegated edits; bolt.diy's browser-local filesystem watcher is not a substitute for the remote worker. Keep this work separate from live browser-use streaming.

Current preview transport still serves through the product API origin. The WebSocket path requires an `Origin` matching the request host and authenticates the preview's project scope, but this does not satisfy the separate-origin security invariant for untrusted generated code; do not consider preview safe for a deployed untrusted-app surface until the origin boundary and browser isolation are implemented and verified. The present relay is Docker-specific, and AWS placement remains undecided. WebSocket runtime/browser acceptance is pending; regression coverage has been added but is intentionally unrun at the user's request.
